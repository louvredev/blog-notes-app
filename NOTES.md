# NOTES.md — Hand-built vs. shadcn/ui

> **Correction:** an earlier draft of this file assumed shadcn's `dialog`
> and `tabs` were built on Radix UI, based on general knowledge of the
> library. The version actually generated by `npx shadcn@latest add dialog
> tabs` in this project uses **Base UI** (`@base-ui/react/dialog`,
> `@base-ui/react/tabs`) instead — shadcn moved some components to Base UI
> in a recent release. This file is corrected to match the real generated
> source in `components/ui/dialog.tsx` and `components/ui/tabs.tsx`.

## Gaps between `playground/Modal.tsx` and shadcn's `Dialog`

1. **Focus trap and scroll lock are internal to the library, not visible
   in the file at all.** shadcn's `DialogContent` is just styling wrapped
   around `DialogPrimitive.Popup`. All of the actual focus-trapping,
   focus-restoration-on-close, and body-scroll-lock logic lives inside
   `@base-ui/react`'s `Dialog.Root`/`Popup` implementation — none of it
   appears in the component source you read. My `Modal.tsx` does the
   opposite: every one of those behaviors (`getFocusableElements`, the Tab
   key handler, the `inert` toggle, the scroll-lock effect) is written out
   by hand and visible in the file. Reading shadcn's source doesn't
   actually show you *how* focus trapping works — it shows you that a
   well-built primitive lets you not think about it at all.

2. **Animation state comes from data attributes I don't emit.** shadcn's
   overlay and popup use `data-open` / `data-closed` classes
   (`data-open:animate-in data-open:fade-in-0`, etc.) driven by Base UI's
   internal open/close state machine, so the exit animation can finish
   *before* the element unmounts. My `Modal` just returns `null`
   immediately when `open` is `false` — there's no exit state, so an exit
   animation isn't possible without restructuring the component to delay
   unmounting.

3. **Composable "render as" pattern for the close button.** shadcn passes
   `render={<Button variant="ghost" size="icon-sm" />}` into
   `DialogPrimitive.Close`, letting Base UI merge its own behavior
   (click-to-close, ARIA attributes) onto an arbitrary styled `Button`
   component. My close button is just a plain `<button>` with `onClick`
   wired manually — functionally equivalent for this simple case, but not
   reusable the way shadcn's composition pattern is if the trigger needed
   to be, say, a custom icon component instead of a native button.

4. **A separate `DialogDescription` component exists as a first-class
   export; I have no equivalent.** shadcn exports `DialogTitle` *and*
   `DialogDescription` as separate pieces, both wired to the dialog via
   Base UI internally. My `Modal` only has a required `title` prop — there's
   no dedicated slot or prop for a description, so it's easy to end up with
   a dialog that has a heading but no explanatory text for screen reader
   users, and nothing in my component would nudge you to add one.

## Gaps between `playground/Tabs.tsx` and shadcn's `Tabs`

5. **Orientation is a first-class prop; mine is horizontal-only.** shadcn's
   `Tabs` accepts `orientation = "horizontal"` and threads
   `data-orientation` through to `TabsList`/`TabsTrigger`, which use
   `group-data-horizontal` / `group-data-vertical` Tailwind selectors to
   restyle and (per the APG pattern) change which arrow keys navigate the
   list — Up/Down instead of Left/Right when vertical. My `Tabs.tsx` only
   implements the horizontal case; ArrowLeft/ArrowRight are hardcoded, so
   supporting a vertical tab list would mean rewriting the key handler,
   not just passing a prop.

6. **State exposed via `data-active` / `data-slot` attributes for styling
   hooks, not just ARIA.** shadcn's `TabsTrigger` styling reads
   `data-active` to change appearance
   (`data-active:bg-background data-active:text-foreground`). That's a
   separate concern from the `aria-selected` attribute Base UI also sets
   for accessibility — the library gives you both a styling hook and an
   accessibility attribute from the same state, decoupled from each other.
   My `Tabs.tsx` conflates them: I just read `tab.id === activeId` directly
   in the JSX to decide both the CSS classes and `aria-selected`, which
   works, but means style and accessibility state aren't independently
   testable/overridable the way shadcn's data-attribute approach is.

## What I didn't miss

To be fair to the from-scratch versions: correct roles, `aria-selected`,
`aria-controls` / `aria-labelledby` pairing, roving `tabIndex`, Home/End
support, Escape-to-close, and focus-return-to-trigger were all things I
got right without a library — and you can *see* all of that logic in my
files, which you can't with shadcn's, since the real work happens inside
`@base-ui/react`. The gaps above are less about "basic correctness" and
more about: (a) defensive behavior for edge cases I never tested against,
and (b) composition patterns that shadcn's Base-UI-backed primitives
support and mine don't.
